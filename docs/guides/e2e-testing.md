# End-to-End Testing with Playwright

The frontend has two test layers with clearly separated jobs. Adding a test to the
wrong one is the most common mistake, so start here.

| Layer | Tool | Runs against | Answers | Lives in |
|-------|------|--------------|---------|----------|
| Unit / component | Vitest + Testing Library + MSW | happy-dom, mocked API | "Does this component render and behave?" | `frontend/src/**/*.test.tsx` |
| **End-to-end** | **Playwright** | Real Chromium/Firefox against the real Vite dev server | "Does a user flow work in a browser?" | `frontend/e2e/**/*.spec.ts` |

**Write a Vitest test by default.** Reach for Playwright only when the thing under
test cannot exist in happy-dom:

- **Routing and the app shell** — TanStack Router navigation, the taxonomy-driven
  sidebar, browser back/forward, deep links.
- **Auth against a real browser** — token persistence in `localStorage`, the silent
  401 refresh in [`src/api/client.ts`](../../frontend/src/api/client.ts).
- **WebGPU** — `navigator.gpu` only exists in a real browser. This is the one
  capability Vitest structurally cannot cover.

## Running the tests

```bash
just fe-e2e-install   # once, after `just fe-install` — downloads the browsers
just fe-e2e           # the default suite: mocked API, no backend needed
just fe-e2e-ui        # interactive Playwright UI (best for writing tests)
just fe-e2e-headed    # watch a real browser drive the app
just fe-e2e-webgpu    # only the GPU specs
just fe-e2e-slow      # real model downloads + real ONNX sessions (minutes)
just fe-e2e-models    # just the model-id check against the HF Hub (seconds)
just fe-e2e-report    # open the HTML report from the last run
```

`just fe-e2e` starts its own Vite dev server, or reuses one you already have
running from `just fe-dev`. You do **not** need Django or Postgres for it — the
default suite stubs the API at the network layer.

### Running against the real backend

Specs tagged `@backend` are excluded by default. To include them:

```bash
just dev              # backend + frontend, in one terminal
just be-seed-e2e      # create/reset the e2e@example.com user
just fe-e2e-full      # sets E2E_BACKEND=1, runs everything
```

`just be-seed-e2e` refuses to run when `DEBUG=False`, so it can never mint a
known-password account against a production database. Override the credentials
with `E2E_USER_EMAIL` / `E2E_USER_PASSWORD`.

Two kinds of `@backend` spec exist:

- **Logging in through the UI** (`auth.spec.ts`) — drives the real login form and
  asserts the real API accepts or rejects the credentials.
- **Starting already signed in** (`authenticated.spec.ts`) — declares
  `test.use({ storageState: "e2e/.auth/user.json" })`. The `setup` project logs in
  once through the real UI and saves that file; every spec after it reuses the
  session instead of paying for another login.

`e2e/.auth/` is gitignored and regenerated by the `setup` project, so a fresh
clone has no auth file. That is fine: the specs which need it are `@backend`-tagged
and filtered out of the default run, so a missing file never breaks `just fe-e2e`.

### Running the slow model specs

Specs tagged `@slow` are excluded by default. They download real ONNX weights
from Hugging Face (80–220 MB per model) and open a real ONNX Runtime session:

```bash
just fe-e2e-slow      # sets E2E_SLOW=1 — ~2.5 min, needs network
just fe-e2e-models    # the cheap half: every model id must resolve (~3 s)
just fe-e2e-enhance   # speech enhancement on both backends (~20 s + download)
```

**These are not optional nice-to-haves.** Two audio bugs shipped past a fully
green unit suite because both lived in exactly what the unit tests mock away:

- every ASR model failed to open a session on the WASM fallback (a quantized
  decoder hit an ONNX Runtime bug), so the *universal* fallback could not load
  a model at all; and
- two classification models pointed at Hugging Face repos that don't exist, so
  the Hub answered 401.

A mocked test cannot see either. `audio-models.spec.ts` asserts that each model
actually reaches "Model ready", and that Whisper transcribes the JFK sample to
the right *words* — a model that loads but decodes garbage is still broken.

`/audio-to-audio` raises the bar again, because its pre/post-processing is ours
rather than Transformers.js's, and wrong DSP produces plausible audio instead of
an error. Its spec therefore **measures**: `e2e/utils/enhance.ts` runs the real
graph in the page over a synthetic noisy clip and asserts the scale-invariant
SDR improves by at least 6 dB. It drives the modules directly via `page.evaluate`
(`import("/src/audio/enhance/session.ts")` — the Vite dev server serves the app's
own TypeScript) rather than the UI, because the route offers no way to read
samples back out and "a waveform appeared" cannot tell good audio from metallic.
The WebGPU half lives in `webgpu/enhance.spec.ts` and skips without a real GPU.

## Layout

```
frontend/
  playwright.config.ts     # projects, webServer, the HTTPS workaround
  tsconfig.e2e.json        # type-checks e2e/ under `npm run build`
  e2e/
    fixtures/
      base.ts              # the extended `test` — import from here, not @playwright/test
      mockApi.ts           # network-level Django stub
      webgpu.ts            # GPU probe + a way to hide navigator.gpu
    pages/                 # page objects
      ModelPage.ts         # the four-slot base — AudioPage and TensorPage extend it
      AudioPage.ts         # + model picker, load/retry, backend readout
      TensorPage.ts        # + matrix operands, result grid readback
      AppShell.ts          # sidebar, navbar, theme
      LoginPage.ts
    specs/                 # the tests
      global.setup.ts      # logs in once, saves storage state for @backend specs
      model-page.spec.ts   # the four-slot contract + the arrangement (§4a geometry)
      audio.spec.ts        # audio routes with downloads blocked — fast, default run
      audio-models.spec.ts # @slow: real weights, real ONNX sessions
      webgpu/              # the GPU-only project
    utils/
      enhance.ts           # in-page enhancement run + SDR measurement
```

### Page objects mirror the page pattern

Every task route renders the same four slots
([`model-page-pattern.md`](../standards/model-page-pattern.md)), so
`ModelPageObject` holds what is true of all of them — `slots`, `slot(n)`,
`outputPanel`, `emptyOutput`, `runningOutput`, `error`, `button(name)`,
`loadProgress`, `cancelLoad`, `cachedBadge(id)` — and the
modality-specific objects extend it rather than repeating it. `AudioPage` adds the
picker, `load()`/`retryButton` and the backend readout; `TensorPage` adds matrix
operands and result-grid readback.

Everything is scoped to `<main>`. The sidebar carries task-category buttons whose
names collide with route buttons — "Computer Vision" matches a `/^Compute/` locator.

**So does anything the browser itself owns.** Cache Storage and `localStorage` are real
here and stubbed in Vitest, which is why the refresh story
([`model-page-pattern.md` §5b](../standards/model-page-pattern.md)) is asserted in
`model-page.spec.ts`: a reload keeps the selected model and downloads nothing; a seeded
`transformers-cache` entry plus a stored intent resumes the load and says "Restoring from
cache…"; the same intent *without* the cache entry does not; and cancelling a stalled
download returns the page to `idle`. Route the Hub to a handler that never responds when a
spec needs a load to stay in flight — aborting races it straight to an error state.

**Layout lives here, and only here.** Vitest runs in happy-dom, which has no layout
engine — every `getBoundingClientRect()` is zeroes — so the *arrangement* half of the
page pattern (§4a: setup rail, workbench columns, breakpoints) can only be asserted in
a real browser. `model-page.spec.ts` owns it: INPUT and OUTPUT horizontally disjoint and
vertically aligned at 1440×900, the OUTPUT panel above the fold, the setup strip above
the work columns at 1000×800, four bands stacking in increasing `y` at 375×812, no
horizontal document overflow at either width, and no chasm between a short input and its
transport row. A route test asserts presence and order; it must never assert pixels.

**Two rules the migration to that pattern added:**

1. **Nothing downloads on navigation.** Weight-loading routes start `idle`, so a spec
   that wants a model must press Load like a user: `await audio.load()`. A spec that
   only asserts the shell should *not* — and `model-page.spec.ts` asserts exactly
   that, with the Hub blocked and every request recorded.
2. **Assert on a UI signal, not on the request list.** After `load()`, the worker
   spawn and the first fetch are both async. Wait for the visible consequence — the
   error, or the ready line — then assert on what was requested.

**Every spec imports `test` and `expect` from `../fixtures/base`**, never from
`@playwright/test` directly. That gives one seam for adding fixtures later
without touching every spec.

Shared response bodies live in
[`src/test/fixtures/models.ts`](../../frontend/src/test/fixtures/models.ts) and are
imported by **both** the MSW handlers and the Playwright mock — so the unit-test
mocks and the E2E mocks cannot drift apart.

## Gotchas

These are the things that will cost you an afternoon if you don't know them.

### The dev server is HTTPS with a self-signed cert

[`vite.config.ts`](../../frontend/vite.config.ts) uses `@vitejs/plugin-basic-ssl`
because `navigator.gpu` is only exposed in a **secure context**. So the config sets
`ignoreHTTPSErrors: true` in **two** places: `use` (for browser contexts) and
`webServer` (for the health check). Miss the second and Playwright hangs for 120s
waiting for a server it can already reach.

### Never route on a `**/api/**` glob

That glob also matches the dev server's own module URLs — `/src/api/client.ts` —
so it replaces the app's API client with JSON and the app never boots. Match on
the pathname instead, which is what `installMockApi` does:

```ts
await page.route((url) => url.pathname.startsWith("/api/"), handler)
```

### The dev server sometimes serves a page that never mounts

Vite occasionally triggers its own full reload (`main.tsx?t=…`) while
re-optimising dependencies, and the reloaded document can arrive before the
optimiser has finished. You get a served-but-empty `#root` that never recovers on
its own. It is a dev-server characteristic, not an app bug — a production build
has no optimiser — but it made roughly one navigation in four fail outright.

`e2e/fixtures/base.ts` wraps `page.goto` so every navigation checks the app
actually mounted and reloads if it didn't. **This is why specs must import `test`
from `../fixtures/base`** and not from `@playwright/test`: a spec that imports
`test` directly gets the unwrapped `page` and will flake.

### Vitest would otherwise swallow the E2E specs

Vitest's default `include` glob matches `**/*.spec.ts`, which covers `e2e/`. The
`test.include`/`test.exclude` block in `vite.config.ts` pins Vitest to `src/`.
**If you change that block, re-run `just fe-test` and check the test count is
unchanged** — a silently shrinking suite is the failure mode.

### The UI is Base UI, not Radix

There are no `data-state` conventions to select on. Prefer `getByRole` and
`getByLabel`. Two specific traps:

- `CardTitle` renders a `<div data-slot="card-title">`, **not** a heading — so
  `getByRole("heading")` will not find a card's title.
- `getByRole("button", { name: "Compute" })` also matches the sidebar's
  **Compute**r Vision category. Scope page-content locators to `page.locator("main")`.

### Native form validation beats Zod in a real browser

The login email field is `type="email"`, so the browser's own constraint
validation rejects a malformed address before react-hook-form ever runs — the Zod
message never renders. happy-dom does no constraint validation, which is why the
unit tests *do* see the Zod message. Assert on `validity.valid` in E2E and leave
the Zod-message assertions to the unit tests.

### WebGPU needs a real GPU, and often a real Chrome

Playwright's default headless build ships **no** `navigator.gpu` at all, so the
`webgpu` project uses `channel: "chromium"`. Even then, a machine with no GPU
device node (no `/dev/dri` — most containers and CI runners) reports `unsupported`.

The GPU specs handle this by skipping themselves:

```ts
test.skip(webgpuStatus !== "ready", `No GPU device (status: ${webgpuStatus}).`)
```

The **degradation** specs deliberately do *not* skip — they stub `navigator.gpu`
to `undefined` via `page.addInitScript` and assert the UI reports the unsupported
state instead of crashing. That is the assertion that matters on a GPU-less runner.

Firefox additionally needs `dom.webgpu.enabled` on Linux/macOS; the config sets it
via `firefoxUserPrefs` so it is not a manual step.

### Blocking a model download needs a URL predicate, not a glob

The fast audio specs assert the route shell without pulling weights, by aborting
every Hugging Face request. Use a predicate on the hostname — the same reason
`**/api/**` is banned above applies to any broad glob:

```ts
await page.route(
  (url) => url.hostname.endsWith("huggingface.co"),
  (route) => route.abort(),
);
```

With the Hub blocked the load *must* fail visibly rather than spin forever, and
`audio.spec.ts` asserts exactly that — it is the degradation test for a user on
a flaky connection.

### Always run Playwright from `frontend/`

Running it from the repo root fails at collection with *"did not expect test() to
be called here"* — `npx` resolves a different `@playwright/test` than the specs
import. Every `just` recipe and npm script already does the `cd`, so this only
bites hand-rolled invocations.

Relatedly, paths in the config and specs are resolved against the **working
directory**, not the config file. `e2e/fixtures/paths.ts` derives an absolute
`AUTH_FILE` from `import.meta.url` for that reason — do the same for any new file
path rather than writing a bare relative string. (Playwright loads these as ESM
here, so `__dirname` is undefined.)

### Firefox needs a system library on Linux

`just fe-e2e-install` runs `playwright install --with-deps`, which installs it. If
you installed browsers without `--with-deps`, Firefox fails to launch and asks for
`sudo apt-get install libgtk-3-0t64`.

## Writing a good spec

- **No `waitForTimeout`.** Wait on locators — `expect()` auto-retries. Use
  `expect.poll()` for values read through `evaluate`.
- **No order dependence.** `fullyParallel` is on; any spec may run first.
- **Mock or await every network call you care about.** `installMockApi` returns
  501 for unmodelled endpoints on purpose, so a newly added API call shows up as
  an obvious failure rather than silently reaching a real server.
- **A new spec must pass three consecutive runs** before you push it. Anything
  less is flaky; fix it or don't land it.
- **Known-issue allowlists carry a fix location.** `smoke.spec.ts` has a
  `KNOWN_CONSOLE_ISSUES` list; each entry names the file to fix. The list should
  shrink over time, never grow silently.

## Debugging a failure

```bash
just fe-e2e-report                       # HTML report: screenshots + video
npx playwright show-trace test-results/<dir>/trace.zip
npx playwright test --project=chromium -g "part of the test name" --headed --debug
```

Traces are captured on first retry, screenshots and video on failure.
